# shared-agent-harness

Локальный агент-харнес, в который несколько человек заходят по JWT и **параллельно
управляют одной общей сессией**. OpenAI-совместимый провайдер, agent loop с четырьмя
инструментами (`bash`, `read`, `edit`, `create`), права на инструменты по ролям,
исполнение в изолированной песочнице и полный аудит в SQLite. Три контейнера, три порта,
HTML-морда без сборки.

```
                       ┌──────────── порт 3000 ─── статика (HTML/CSS/JS)
браузер ───────────────┤
                       └──────────── порт 8000 ─── API: auth, сессии, agent loop, SSE
                                          │
                                          ├── HTTPS ──> LLM-провайдер (сеть edge)
                                          │
                                          └── порт 9000 ──> executor (сеть sandbox,
                                                            internal: true, наружу
                                                            НЕ публикуется)
```

**Порт исполнителя намеренно не опубликован.** `bash + edit + create` — это выполнение
произвольного кода по определению; JWT проверяет API, а не executor. Опубликовать 9000
значило бы отдать RCE без аутентификации всей локальной сети.

---

## Запуск

```bash
cp .env.example .env
```

Заполните `.env` (минимум — `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `JWT_SECRET`), затем:

```bash
docker compose up -d --build
```

Морда: http://localhost:3000 · вход `admin` / `ADMIN_PASSWORD` из `.env` (по умолчанию `admin`).

Проверка, что всё поднялось:

```bash
curl -s http://localhost:8000/api/health
```

Отдаёт состояние SQLite, доступность модели у провайдера и свободные мощности песочницы.

### `LLM_BASE_URL` — частая ошибка

Нужен **корень API**, а не путь до метода: `/chat/completions` код добавляет сам.

```
✔  https://api.neuraldeep.ru/v1
✘  https://api.neuraldeep.ru/v1/chat/completions
```

Провайдер на самой машине (Ollama, LM Studio, vLLM) адресуется как
`http://host.docker.internal:11434/v1`, а не `localhost` — внутри контейнера `localhost`
это сам контейнер.

### Локальная сеть

`BIND_ADDR=0.0.0.0` открывает харнес коллегам. Морда сама вычисляет адрес API как
`http://<хост-из-адресной-строки>:8000`, поэтому по `http://192.168.x.x:3000` всё работает
без правок. `BIND_ADDR=127.0.0.1` закрывает доступ на одну машину.

Трафик идёт по HTTP: JWT летит по сети открытым текстом. Для локального демо приемлемо,
для чего-то большего нужен TLS.

## Роли и права

Права выдаются **на инструменты**, через связь `role_tool`, а не колонками в таблице.
Новый инструмент — это строка в `tools` плюс строка в `role_tool`, без `ALTER TABLE`.

| роль | bash | read | edit | create | list_tools |
|---|---|---|---|---|---|
| `admin` | ✔ | ✔ | ✔ | ✔ | ✔ |
| `developer` | — | ✔ | ✔ | ✔ | ✔ |
| `read` | — | ✔ | — | — | ✔ |

Ключевое: список инструментов, уходящий провайдеру, **режется правами роли**. Пользователь
с ролью `read` не получает `bash` в списке вовсе — модель не может вызвать то, чего не
видит. Это надёжнее, чем запрещать вызов постфактум, и заменяет отдельный «аналитический»
запрос к модели «нужен ли инструмент» (в OpenAI-формате он не нужен: модель сама
возвращает либо `content`, либо `tool_calls`).

### JWT

В токене только `sub`, `jti`, `exp`. Роль, `status` и окно дат намеренно **не** кладутся в
токен: он stateless и не отзывается, а блокировка должна срабатывать сразу. Права
читаются из БД на каждом запросе и ещё раз непосредственно перед каждым вызовом
инструмента — между этими точками есть сетевой раунд-трип к провайдеру, за который админ
мог поменять роль.

## Пайплайн одного хода

```
init      создание сессии: probe провайдера + модели, capacity песочницы,
          uuid4 сессии, запись session_init в журнал
   │
   ▼
queue     сообщение встаёт в FIFO-очередь сессии; ход = сообщение одного автора
   │
   ▼
query     контекст собирается из журнала; список тулов = tools ∩ права роли
   │
   ▼
tool?     нет tool_calls -> ход закончен текстом
   │ да
   ▼
safety    allowlist команд + path jail + проверка прав ещё раз из БД
   │      отказ -> в журнал 'blocked' и МОДЕЛИ уходит tool-сообщение с причиной
   ▼
execute   в песочнице: своя группа процессов, таймаут, killpg, обрезка вывода
   │
   ▼
answer    результат в журнал -> следующая итерация (лимит MAX_ITERATIONS)
```

### Общая сессия и параллельное управление

Сообщения нескольких людей встают в одну очередь и обрабатываются **по одному**. Это не
упрощение, а требование формата: между `assistant` с `tool_calls` и его `tool`-результатами
нельзя вставить чужое сообщение — следующий запрос к провайдеру вернёт 400. Заодно права
на инструменты однозначны: это права автора хода, без эскалации через общую сессию.

Все участники видят один поток событий через SSE и могут прервать текущий ход кнопкой
«стоп» (отмена доходит до песочницы и убивает группу процессов).

## База

Шесть таблиц: `roles`, `tools`, `role_tool`, `users`, `sessions`, `events`.

`events` — append-only журнал, который работает сразу как три вещи:

* **контекст для LLM** — проекция по `session_id ORDER BY id`;
* **аудит** — та же таблица без фильтра, с причинами отказов safety-check;
* **лента для морды** — `WHERE id > last_seen_id`, поэтому разрыв SSE не теряет и не
  дублирует события.

Две детали, без которых агент не переживает рестарт:

* `tool_call_id` — ключ склейки вызова с результатом. Без него массив сообщений
  OpenAI-формата не восстановить из БД в принципе.
* `status` — строка `tool_call` заводится как `pending` **до** запуска инструмента и
  закрывается обновлением на месте. Упавший на середине процесс оставляет видимый
  незакрытый вызов, который при старте закрывается синтетическим результатом
  (`recover_pending`), а не подвешивает сессию навсегда.

Настройки SQLite: WAL, `synchronous=NORMAL`, `busy_timeout=5000`, один писатель под локом.

### Смотреть базу через DBeaver

SQLite — это файл, а не сетевой сервис: `http://localhost:8000/...` в поле JDBC URL не
подойдёт. Файл лежит в docker-томе `harness_dbdata`, на диске Windows его нет.

**Вариант 1 — снимок (безопасно, рекомендую).** Делает консистентную копию с учётом WAL:

```bash
docker compose exec -T api python -c "import sqlite3; s=sqlite3.connect('/data/harness.db'); d=sqlite3.connect('/data/snapshot.db'); s.backup(d); d.close(); s.close()"
```

```bash
docker compose cp api:/data/snapshot.db C:/harness-data/harness-snapshot.db
```

В DBeaver: `New Connection → SQLite → Path = C:\harness-data\harness-snapshot.db`.
Поле «JDBC URL» заполнять руками не нужно, драйвер соберёт `jdbc:sqlite:` сам.

**Вариант 2 — живая база.** Оверлей кладёт БД в обычную папку Windows:

```bash
docker compose -f docker-compose.yml -f docker-compose.dbeaver.yml up -d
```

Папка должна быть **вне OneDrive**: sync-клиент не понимает WAL/SHM и способен повредить
базу. Bind-mount на Windows идёт через слой виртуализации с другой семантикой блокировок —
для просмотра годится, для нагрузки нет. Подробности и порядок переноса — в комментариях
`docker-compose.dbeaver.yml`.

## Безопасность исполнения

Строковый safety-check — первый дешёвый слой, а не граница. Блэклист символов обходится
тривиально и при этом не ловит опасное: в `rm -rf /` нет запрещённых символов. Поэтому:

* **allowlist первой команды** каждого сегмента конвейера, а не блэклист символов;
* **path jail** — `realpath` и проверка принадлежности `/workspace` (снимает `..` и
  симлинки наружу); авторитетная проверка — на стороне executor, не API;
* **настоящая граница — контейнер**: non-root (uid 10001), `cap_drop: ALL`,
  `no-new-privileges`, `read_only` rootfs, `mem_limit`, `pids_limit` (форк-бомба),
  сеть `internal: true` (у песочницы нет выхода в интернет), таймаут + `killpg`,
  обрезка вывода до `MAX_OUTPUT_BYTES`.

Инструменты описаны в таблице `tools` как **данные** (описание + JSON Schema), но их
исполнение — код в `executor`. Добавить строку в `tools` через морду и получить новый
исполняемый инструмент нельзя: это был бы RCE поверх собственной аутентификации.

## Известные ограничения

* **Один воркер uvicorn.** Состояние сессий и pub/sub живут в памяти процесса. Для
  нескольких воркеров нужен внешний брокер и лок в БД/Redis.
* **SSE через проброс портов Docker Desktop на Windows стартует с задержкой ~16 с.**
  Измерено: изнутри контейнера тот же стрим отдаёт первый байт за 1 мс, с хоста —
  за 16.7 с (стабильно, независимо от объёма); тот же код без Docker на хосте —
  171 мс. Обычные, не-стриминговые запросы через тот же проброс идут мгновенно.
  Поэтому морда **не полагается на SSE для отрисовки истории**: журнал грузится
  обычным `GET /events?after=`, а поверх работает опрос раз в 2 с как страховка.
  SSE остаётся быстрым путём доставки. Append-only лог с монотонным `id` делает
  оба источника идемпотентными — ни дублей, ни пропусков.
* **Модель пинится к сессии** при создании — это нужно для воспроизводимости журнала.
  Если провайдера переключили, старая сессия остаётся привязанной к недоступной модели;
  меняется селектором модели в шапке (`PATCH /api/sessions/{id}`).
* **Нет стриминга токенов.** Ответ приходит целиком; живость даёт журнал событий. Сделано
  осознанно: при стриминге аргументы `tool_calls` приходят фрагментами и собираются по
  `index` (а не по `id`, которого нет в последующих чанках) — источник тонких багов.
* **Нет обрезки контекста.** При длинной сессии в модель уедет весь журнал; есть только
  лимит итераций.
* **Нет ACL на сессию.** Любой аутентифицированный пользователь видит любую сессию;
  различаются только права на инструменты.
* **Ретраится только `GET /models`.** `chat/completions` не ретраится намеренно: повтор
  после уже выполненного инструмента означал бы двойное исполнение побочных эффектов.

## API

| метод | путь | кто |
|---|---|---|
| `POST` | `/api/auth/login` | все |
| `GET` | `/api/auth/me` | авторизованные |
| `GET` | `/api/models` | авторизованные |
| `GET` | `/api/health` | все |
| `POST` `GET` | `/api/sessions` | авторизованные |
| `GET` `PATCH` | `/api/sessions/{id}` | владелец / админ на PATCH |
| `GET` | `/api/sessions/{id}/events?after=` | авторизованные |
| `GET` | `/api/sessions/{id}/stream?after=` | авторизованные (SSE) |
| `POST` | `/api/sessions/{id}/messages` | авторизованные |
| `POST` | `/api/sessions/{id}/cancel` | авторизованные |
| `GET` `POST` `PATCH` | `/api/admin/users` | `admin` |
| `GET` | `/api/admin/{roles,tools,logs,stats}` | `admin` |

Токен передаётся заголовком `Authorization: Bearer`. SSE читается через `fetch` +
`ReadableStream`, а не `EventSource`: последний не умеет кастомные заголовки, а тащить JWT
в query string значит светить его в логах.
